# S1 — Encryption design for DataEater v1

**Status: design only. No code until this is agreed.**

Agreed with the project owner on 5 October 2026. The goal is deliberately
small: **encrypt a database, and let a customer unlock it offline by entering
a code the creator sent them.** Not a DRM platform.

> ### One part of this document is now out of date
>
> This is the original design record and is kept as written. But **section 13's
> Ed25519 signing key was replaced by ECDSA P-256 with SHA-256** before any of
> this was built, because Ed25519 turned out to be unverifiable on many real
> Android phones — including the development phone.
>
> Measured on that phone, none of its seven registered crypto providers offers
> Ed25519, so every Unlock Code was refused. ECDSA P-256 works everywhere.
>
> **Do not implement from this section as written.** Everything else here is
> still accurate. For what is actually built, see
> [SECURITY.md](https://github.com/verum001/DataEater/blob/main/docs/SECURITY.md) and `packaging.py` / `DeviceKeys.kt`.
>
> Reason and evidence: [SECURITY.md](https://github.com/verum001/DataEater/blob/main/docs/SECURITY.md#the-one-bug-the-cross-language-tests-caught).

## 1. The flow, as agreed

```
DATABASE BUILDER
      │
      ├── creates a normal .dataeater
      │
      └── optional: encrypt it
              │
              ▼
        creator sets a secret + optional expiry
              │
              ▼
        encrypted .dataeater  ──►  customer

CUSTOMER opens the app
      │
      ▼
🔒 This database is encrypted.
   Contact the creator: example@company.com
   Your Unlock Request Code: ABCD-1234-WXYZ
      │  (sent by email or messenger)
      ▼
CREATOR pastes the code into the licence generator
      │
      ▼
UNLOCK-EFGH-5678
      │  (sent back)
      ▼
CUSTOMER enters the Unlock Code ──► database opens, offline
```

### Naming, as agreed

| Name | Meaning | Cryptographic significance |
|---|---|---|
| **Unlock Request Code** | shown to the customer, sent to the creator | **none** — it only identifies the customer and the order |
| **Unlock Code** | sent back by the creator | **this is the secret** |
| *(the internal key)* | generated by the software | never shown, never sent, never stored anywhere |

The customer's email thread never contains the actual database key in
readable form, and the creator never has to handle a raw key.

## 2. ⚠️ The one hard problem: a short code cannot carry a key

The agreed flow implies an unlock code shaped like `UNLOCK-EFGH-5678`.

**That cannot work.** An encryption key is 256 bits of random data. Written
out, that is roughly 43 characters of base32 or 52 of base64. There is no way
to fit a real key into a short human-friendly code without a second secret,
and there is no second secret available — the creator does not remember one.

### Three ways out, and which one we take

| Option | How it works | Result |
|---|---|---|
| **A. The Unlock Code is the secret itself** | the creator chooses a passphrase when encrypting, and that passphrase *is* the unlock code | ✅ **chosen** — simple, honest, no hidden state |
| B. Short code + a server | the code is looked up on a server that holds the key | ❌ breaks offline-first |
| C. Short code + a fixed built-in key in the app | a key shipped inside the APK | ❌ trivially extracted; gives false security |

**So the Unlock Code will look something like:**

```
UNLOCK-7K3M-9QX2-VB8T-5HNF-2RWD-JP6C-YT4B-XK9N
```

Longer and less friendly than hoped — **and that is a fact about encryption,
not a design choice we can talk our way around.** We can:

* make it easy to **copy and paste**, so the user never types it by hand
* group it so it can be read aloud over the phone if needed
* say plainly in the interface that it is long *for a reason*

## 3. What is actually encrypted, and what is not

### Readable — the app must be able to explain before any key exists

`manifest.json`, with **only non-sensitive fields**:

```json
{
  "format": "dataeater",
  "format_version": 1,
  "database_id": "example-machinery",
  "name": "Example Machinery Database",
  "description": "Service information for Example equipment.",
  "language": "en",
  "encryption": "aes-256-gcm",
  "creator": "Example Company",
  "contact": "example@company.com",
  "expiry": "never",
  "counts": { "documents": 2, "chunks": 944 }
}
```

Nothing here reveals the knowledge inside. That is the point: the app can say
*"this is locked and here is who to ask"* **without decrypting anything**.

### Encrypted — the actual knowledge

| File | Encrypted? |
|---|---|
| `manifest.json` | ❌ readable, public fields only |
| `sources.json` | ✅ encrypted |
| `chunks.jsonl` | ✅ encrypted |
| `payload.enc` | ✅ the two above, stored as one AES-GCM blob |

Document **titles** are inside the encrypted part, because a title such as
*"Hydraulic Pump — Torque Settings"* already tells a competitor something.

## 4. The cryptography, using one established library

### One library on each side, used as intended

| Side | Choice | Why |
|---|---|---|
| **Builder (Python)** | `cryptography` | the reference Python crypto library; audited, maintained, already the kind of dependency we are willing to have |
| **App (Android)** | **platform JCE (`javax.crypto`)** | AES-GCM and ECDH are **built into Android**. No new dependency at all. |

### The exact scheme

> **Corrected 5 October 2026.** An earlier draft of this section said the
> content key was *derived* from a passphrase with PBKDF2-HMAC-SHA256. That was
> the design *before* device binding was added, and it no longer applies.
> **PBKDF2 is not part of the current design.** The content key is random,
> and device binding is done with ECDH + HKDF (section 7b). The table below
> is the only current version.

```
1.  CREATOR generates a RANDOM 32-byte content key        (CSPRNG)
2.  chunks.jsonl + sources.json  ──►  payload.bin          (a small envelope)
3.  payload.bin  ──AES-256-GCM──►  payload.enc            (random 12-byte nonce)
4.  the nonce is stored alongside payload.enc              (public, no secret)
5.  the content key is later WRAPPED per device            (section 7b)
6.  each customer receives a signed Unlock Code            (sections 7b and 13)
```

**Every one of these is a published standard.** No custom algorithm is
invented anywhere.

### Why the content key is random and not derived

Storing a key derived from a human passphrase is only necessary when a human
types the secret. Here **no human ever types a secret**, so there is nothing
to protect against guessing — and a random key is strictly stronger.

It also gives the separation that matters:

```
content key  = protects the DATABASE     one per database, made once
device key   = protects the LICENCE      one key pair per phone
```

A second customer needs only a second wrapping — **no re-encryption**.

## 5. Expiry

> **Corrected 5 October 2026.** This section previously said expiry is written
> *inside the encrypted database payload*. That is no longer correct.
> **Expiry belongs to the signed Unlock Code**, because different customers
> may receive different terms from the *same* database. See also the note
> directly below on why this is still tamper-proof.

Expiry is **part of the licence**, not part of the database.

```
Customer A  →  signed Unlock Code  →  1 year
Customer B  →  signed Unlock Code  →  never
Customer C  →  signed Unlock Code  →  90 days
```

All three use **one** encrypted database, with no re-encryption.

### The agreed options

| Choice | Expiry stored in the signed Unlock Code |
|---|---|
| ○ Never expires *(default)* | `null` |
| ○ 30 days | today + 30 days |
| ○ 90 days | today + 90 days |
| ○ 1 year | today + 365 days |
| ○ Custom | a date the creator types |

### Why this is still tamper-proof

The earlier objection to putting expiry in the readable manifest was that
anyone could open the file in an editor and change `"expiry": "never"`.

**The signed Unlock Code closes that hole.** The expiry is covered by the
creator's Ed25519 signature, so editing it invalidates the signature and the
app refuses the code. A customer cannot extend their own licence because they
cannot re-sign it.

Putting expiry in a **signed** licence is therefore *safer* than putting it in
an unsigned manifest, while also allowing different terms per customer.

### Pricing tiers come later, not from new code

| Tier | What the creator chooses |
|---|---|
| evaluation | 30 days |
| annual | 1 year |
| permanent | never expires |

All three are the *same* mechanism with a different date. **No change to the
design, none to the app.** That was the point of separating expiry from the
cryptography.

## 6. What the app needs to know — and nothing more

This is the abstraction you asked for, and it is the right one:

```
Is this database encrypted?
        │
        ├─ no  ──► open it, as today
        │
        └─ yes
             │
             ├─ is a valid Unlock Code already stored for this device?
             │        ├─ yes ──► decrypt and open
             │        └─ no  ──► show "contact the creator"
             │                  show the Unlock Request Code
             │                  wait for the Unlock Code
             │
             └─ then ──► decrypt, read expiry, refuse if past the date
```

The Android app never sees a key type, a curve, or a nonce. It sees a boolean
and a code.

## 7. Honest limits of this design

| Achieved | Not achieved |
|---|---|
| casual copying prevented | ❌ **a customer can screenshot, retype, or share their database file after unlocking** |
| the creator keeps the secret | ❌ **the Unlock Code is reusable** — if a customer gives it to a friend, that friend has a valid licence |
| modification is detectable | ❌ an app can be patched to ignore expiry |
| fully offline | ❌ **no revocation.** A code that was valid once stays valid on that device |

### The two that matter most, and what we could do about them

**1. The Unlock Code can be shared.** Anyone holding it can unlock the
database. That is a direct consequence of keeping the system simple, and it is
the honest price.

*If it turns out to matter later*, the fix is to make the code
**device-bound** — a few more moving parts, which is exactly why it is not in
v1. **Recorded, not forgotten.**

**2. Expiry can be bypassed by patching the app.** This is the standard
limit of anything that decrypts data on the user's own device. **We will
document it plainly rather than pretend it away.**

### What is genuinely achievable

Realistically, this stops a customer from:

* opening the file in a text editor to copy the text
* emailing the `.dataeater` file to a colleague without a licence
* publishing the knowledge as their own

It does **not** survive an experienced attacker with a rooted phone. **No
client-side design ever will.**

## 7b. Device binding — agreed improvement

**Agreed on 5 October 2026**, after reviewing the limits in section 7. Binding
a licence to one device removes the worst weakness: *an Unlock Code could be
passed to a friend.*

### The idea

The Unlock **Request** Code stops being just a name. It carries a **public key
generated by the phone**. The Unlock Code carries the content key **encrypted
to that public key only**.

```
CREATOR
  │
  ├── generates a RANDOM content-encryption key for the database
  │     (32 bytes, from the system CSPRNG - never derived from anything)
  │
  ├── encrypts the database payload with that key  (AES-256-GCM)
  │
  └── wraps that same key for the customer's public key
          │
          ▼
      Unlock Code
```

### Why the content key is random and not derived

**Correction agreed on 5 October 2026.** An earlier draft said *"the creator
derives the content key"*. That is wrong, and the difference matters.

| | random content key ✅ | derived from the customer's key ❌ |
|---|---|---|
| Separates database encryption from device authorisation | **yes** — two independent jobs | no — tangled together |
| Issue a second licence for a second device | re-use the same content key, wrap it again for the new key pair | the second device would need its own content key and the whole database re-encrypted |
| Change a licence policy | wrap, nothing else | re-encrypt everything |

**Clean separation, in one line:**

```
content key  = protects the DATABASE        (one key per database)
device key   = protects the LICENCE         (one key pair per phone)
```

The only thing that travels between the two is *the content key, wrapped for
one particular phone*.

```
PHONE (first run)
   generates a key pair
   private key: generated on the phone and NEVER leaves it
   public key:  put into the Unlock Request Code
        │
        │  Request Code  (the public key, nothing secret)
        ▼
CREATOR
   derives the content key
   encrypts it to the phone's public key
        │
        │  Unlock Code  (the content key, locked to that phone)
        ▼
PHONE
   decrypts with its own private key
   ✅ works
```

**A second phone holds a different key pair, so the same Unlock Code does
nothing there.** The friend problem is gone, as far as is realistically
possible on a device the user controls.

### What must never happen

> **The private key must never leave the phone, and must never appear in the
> Request Code, the Unlock Code, the database, the APK or the repository.**

That is the whole reason for using *asymmetric* cryptography here. An earlier
idea — sending a random device "secret" in the Request Code — was rejected
because that secret would travel in the email, and anyone who could read the
email could then unlock the database themselves.

### Two standard ways to do this

| | **ECDH on P-256** *(recommended)* | RSA-2048 |
|---|---|---|
| How the key is wrapped | ephemeral ECDH → HKDF → AES-GCM | RSA-OAEP with SHA-256 |
| Request Code length | **~104 characters** | **~470 characters** |
| Request Code transport | fits comfortably in an email | long, but still just an email |
| Known issue | ECDH with `AndroidKeyStore` EC keys has had encoding problems in the past | none — very well trodden |
| Standard | NIST P-256, RFC 5869 (HKDF), RFC 3394 | PKCS #1 v2.2 |

**Recommendation: ECDH P-256**, because a Request Code a customer can read and
copy without frustration is worth a great deal.

> ⚠️ **But we must not commit to it untested.** Before writing the builder, run
> a small spike on the actual phone: generate an EC P-256 key pair, do an ECDH
> exchange with a key held in `AndroidKeyStore`, and unwrap a value produced by
> Python. **Half a day, and it either works or it does not.**
> If it does not, fall back to RSA-2048-OAEP, which is duller but certain.

### How the private key is kept

* **First choice:** `AndroidKeyStore`, which can keep an EC key **hardware-backed**
  and **non-exportable** — the phone physically cannot copy it out.
* **If the spike shows Keystore ECDH is troublesome:** store the private key
  encrypted at rest with an AES key held in `AndroidKeyStore`, so it is still
  never readable from a backup or a file dump.

Either way the key is tied to the device: uninstalling the app and reinstalling
it means a **new** Unlock Request Code, and the old licence stops working.

### What this changes, and what it costs

| | Before | After device binding |
|---|---|---|
| Friend cannot use the licence | ❌ could | ✅ **different private key, unwrap fails** |
| Unlock Code is reusable | ❌ yes | ✅ **only on the issuing device** |
| Creator must handle each sale | one code | one code **per customer device** |
| Customer changes phone | works | **needs a new code from the creator** |
| Request Code length | short | ~104 characters (ECDH) |

**The operational cost is real and must be stated plainly to customers: a
licence is issued per device, and changing phones needs a fresh code.** That is
the price of the protection, and it is a fair trade for anything that can be
resold.

### Error message when the device does not match

The app must say this plainly rather than showing a generic failure:

```
This Unlock Code was issued for a different device.

Ask the creator for a new code for this phone, then enter it here.
```

That is a common and legitimate situation, and a clear message turns it from
confusion into a two-minute fix.

## 8. Build order, once this is agreed

0. **spike:** prove ECDH P-256 works on the target phone before anything else
1. builder: `encrypt` — add `encryption` and the public fields to the manifest
2. builder: encrypt the payload with AES-256-GCM
3. **tests**: round trip, wrong code, tampered payload, truncated file
4. app: detect `encryption != "none"` and show the locked screen
5. app: generate and show the Unlock Request Code
6. builder: `licence` — turn a request code into an unlock code
7. app: accept the code, derive the key, decrypt
8. app: read expiry and refuse when past the date
9. **tests for every negative case**: wrong code, wrong device, expired, tampered, replayed

Steps 3 and 9 come before the UI so the crypto is proven on the computer
first, in seconds, before anything reaches a phone.

---

### A rejection worth recording

An earlier idea was to have the phone put a **random device secret** into the
Request Code, and have the creator encrypt the content key to that secret.

**It was rejected.** With symmetric cryptography that secret would travel
inside the email, so anyone who could read the email could decrypt the
database themselves. A public key travels in the email safely because the
matching private key never leaves the phone.

That single point is why device binding must use asymmetric cryptography, not
a shared secret.

The example given was:

```json
{ "format": 1, "name": "...", "version": 3, ... }
```

DataEater's existing format uses different field names, and the app already
reads them:

```json
{
  "format": "dataeater",        ← the string, not a number
  "format_version": 1,          ← this is the "version" field
  "name": "...",
  ...
}
```

**We must not change the existing field names** — the app, the builder, the
tests and the documentation all depend on them. Only *new* fields (`creator`,
`contact`, `expiry`) are added, and they are optional, so every existing
database keeps working unchanged.

## 13. The creator signing key (Ed25519)

**Agreed 5 October 2026.**

Device binding alone (section 7b) proves a licence is *built for this phone*.
It does not prove *who issued it*. The Ed25519 key supplies that.

### Two keys, two jobs

| Key | Job | Algorithm |
|---|---|---|
| **content key** | protects the database payload | random 32 bytes, AES-256-GCM |
| **device key** | proves the licence is meant for one phone | P-256 key pair in AndroidKeyStore |
| **creator signing key** | proves the creator issued this licence | Ed25519 |

### Where the signing keys live

| Item | Where | Rule |
|---|---|---|
| Ed25519 **private** key | creator's secret file | **never** in the database, the APK, the repository, or sent to a customer |
| Ed25519 **public** key | readable `manifest.json` | safe to distribute; the app needs it to verify |
| content key | creator's secret file | needed again for every future licence; **lose it and no new customer can be licensed** |

A private creator key file in v1 is acceptable. Better storage (a passphrase
protecting the key, or a hardware token) can come later without changing the
format, because only the file's location changes, never the protocol.

### What the signature covers

The Ed25519 signature is made over the whole licence, so nothing in it can be
altered without detection:

```
signs: { database_id,
         content key wrapped for this device,
         expiry }                 ← signed, so it cannot be edited
```

Because the expiry is signed, a customer cannot extend their own licence.
That is what replaced the earlier protection of burying the expiry inside the
encrypted payload.

## 12. Summary of the agreed v1 design

| Aspect | Decision |
|---|---|
| **Who holds the secret** | the database creator only |
| **What the customer sends** | Unlock **Request** Code — carries the phone's **public** key |
| **What the creator returns** | Unlock Code — the content key, encrypted **to that phone only** |
| **Device binding** | ✅ yes — a second phone has a different key pair and cannot unlock |
| **Key algorithm** | ECDH P-256 *(first choice)*, RSA-2048-OAEP *(fallback)* — settled by the spike |
| **Content encryption** | AES-256-GCM with a **random** 32-byte content key |
| **Device wrapping** | ECDH P-256 + HKDF-SHA256 |
| **Licence authentication** | **Ed25519** creator signing key; public key in the manifest |
| **Expiry** | **inside the signed Unlock Code**, default **never**; 30/90/365 day tiers |
| **Readable without a key** | the manifest, public fields only |
| **Expiry** | inside the encrypted payload; default **never**; 30/90/365 day tiers |
| **Libraries** | `cryptography` in Python, **Android platform only** on the app side |
| **New Android dependencies** | **none** |
| **Offline** | ✅ always |
| **Revocation** | ❌ not in v1 |
| **Per-device** | ✅ yes — one licence per device |

### The two honest limits that remain

1. **A customer who has unlocked the database can copy its content out.**
   Nothing on the customer's own device can prevent that.
2. **A patched app can ignore expiry.** Standard for anything that decrypts
   locally.

Everything a realistic buyer needs — stopping casual copying, proving who the
creator is, and preventing a licence from being resold — **is** achieved.
